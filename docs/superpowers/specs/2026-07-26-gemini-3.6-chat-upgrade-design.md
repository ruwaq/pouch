# Spec — Gemini 3.6 Flash Chat Upgrade

> **Date:** 2026-07-26 · **Status:** Design · **Build queue item:** #2
> **Goal:** Switch the chat model to `gemini-3.6-flash` from a single source of truth, and unlock the quality jump the new model enables — without breaking on the thinking-model quirks that bit prior migrations.

---

## Problem

The chat LLM is pinned to `gemini-3.5-flash` in **4 separate hardcoded locations** plus an env override, and the codebase carries comments asserting *"only 3.5 works, 2.5/2.0 return 404"*. This is exactly the trap that caused prior model migrations to break: change one site, miss another, and the app silently uses a stale model. Two independent problems compound it:

1. **No single source of truth for the model name.** `factory.ts` (chat default), `app.ts:112` (health probe), `.env` (override), and stale comments all hold their own copy. The `/health` probe even hardcodes its own URL and ignores `LLM_MODEL`, so it can report "ok" while the chat uses a different model.
2. **No request tuning.** `gemini-provider.ts` sends only `systemInstruction` + `contents` + `tools`. There is no `generationConfig`, no multi-turn `contents` (history is inlined as text), and no `AbortController`/timeout. The model is being used at its lowest possible quality.

### The 3.6 Flash wrinkle (verified empirically)

Confirmed by live test against the production API key on 2026-07-26: `gemini-3.6-flash` returns **HTTP 200 in ~0.95s** (faster than 3.5's ~2.8s on the same key). **But it is a thinking model**: with `maxOutputTokens: 256`, a request returned `candidatesTokenCount: 11` (visible) and `thoughtsTokenCount: 241` (hidden reasoning), and the visible reply was truncated mid-sentence (`finishReason: MAX_TOKENS`). Thinking tokens and answer tokens draw from the **same** `maxOutputTokens` budget. A naive migration (swap the string, keep the absent/tiny config) produces truncated replies.

This is the failure mode the user wants to avoid ("que funcione, no caer en el error de otros modelos"). The design must size `maxOutputTokens` for thinking + answer, and the response parser must tolerate `thoughts` parts without surfacing them.

## Design

### 1. Single source of truth for the model name

**One constant, one place.** Introduce `DEFAULT_LLM_MODEL = 'gemini-3.6-flash'` in `packages/infra-ai/src/factory.ts`, exported alongside the factory. Selection rule, unchanged in shape:

```
effectiveModel = (config.LLM_MODEL?.trim()) || DEFAULT_LLM_MODEL
```

- `app.ts` `/health` probe **stops hardcoding** the URL. It imports `DEFAULT_LLM_MODEL` from `@pouch/infra-ai` and resolves the runtime model the same way the factory does (`process.env.LLM_MODEL?.trim() || DEFAULT_LLM_MODEL`), then builds the probe URL from that. This kills the divergence bug. (The factory's resolution logic is extracted into a tiny exported `resolveLlmModel(config)` helper so both call sites share one function, not just one constant.)
- Stale "only 3.5 works / 2.5 returns 404" comments in `gemini-provider.ts` and `factory.ts` are replaced with a single accurate comment: model is configurable via `LLM_MODEL`, default `gemini-3.6-flash` (verified working 2026-07-26).
- `.env` and `.env.example` `LLM_MODEL` updated to `gemini-3.6-flash` with a comment noting it's the verified default.
- Test fixtures currently using `'gemini-2.0-flash'` as a string are updated to a clearly-fake `'test-model'` so no test accidentally asserts on a real model name.

### 2. `generationConfig` tuned for a thinking model

Add a `generationConfig` block to **both** `generateWithTools` and `generateText` in `gemini-provider.ts`:

```ts
generationConfig: {
  temperature: 0.7,        // warm but deterministic enough for tool routing
  topP: 0.95,
  maxOutputTokens: 2048,   // room for thinking + answer (3.6 spent 241 on thoughts alone)
  // thinkingConfig intentionally left at the model default (enabled) — we WANT the reasoning.
}
```

- `2048` is chosen because the worst observed case (a simple greeting) spent 241 thinking tokens; a real cash-out/education reply needs headroom for both reasoning and a 2-3 sentence answer. This is a safe floor, not a ceiling.
- `temperature: 0.7` matches the system prompt's "warm, concise" personality. Intent parsing benefits from lower temperature but function-calling is robust at 0.7 with Gemini; we keep one config for simplicity and revisit if routing misfires.
- **Response parsing must skip `thoughts` parts.** Today the parser takes `candidates[0].content.parts[0]`. With thinking enabled, `parts` may contain a `{thought: true, text: "..."}` part before the real answer. New rule: iterate `parts`, return the first part that is a `functionCall` OR a `text` part **without** `thought: true`. Add a regression test for a response that leads with a thoughts part.

### 3. `AbortController` timeout (closes audit item L6)

Every Gemini `fetch` gets a timeout. The shared `packages/shared/src/http.ts` already has timeout plumbing; align with its pattern:

```ts
const controller = new AbortController();
const timeout = setTimeout(() => controller.abort(), GEMINI_TIMEOUT_MS);
try {
  const res = await fetch(url, { ..., signal: controller.signal });
} finally {
  clearTimeout(timeout);
}
```

- `GEMINI_TIMEOUT_MS = 15_000` (15s). 3.6 replies in ~1-3s; 15s is generous for a thinking model under load without letting a hung connection freeze the demo. On abort → return `err(toTimeoutDomainError)` so the agent falls back to the template reply (existing behavior).
- This is also the foundation for item #6 (H6 timeouts on web3 calls) — same pattern, different constant.

### 4. Multi-turn `contents` (real conversation memory)

Today `LlmReplyStrategy.buildPrompt` inlines the last N messages as a `"Recent conversation:"` text block. Replace this with proper Gemini multi-turn `contents`:

```ts
contents: [
  { role: 'user',      parts: [{ text: msg1 }] },
  { role: 'model',     parts: [{ text: reply1 }] },
  { role: 'user',      parts: [{ text: msg2 }] },
  // ...up to MAX_HISTORY turns
  { role: 'user',      parts: [{ text: currentMessage }] },
]
```

- Gemini uses `role: 'model'` (not `'assistant'`) for the AI's turns. Get this right or the API 400s.
- `MAX_HISTORY` stays at 10 turns (existing constant in `agent-chat-service.ts:48`). Older history is dropped, not inlined — the API handles context.
- The system prompt stays in `systemInstruction` (it already is). The per-scenario framing text that `buildPrompt` currently prepends (`"Reply to this greeting..."`, `"Summarize this balance..."`) stays as the **final user turn's** prefix, since it's scenario-specific guidance, not system-level.
- `generateWithTools` (intent parsing) keeps sending only the latest message as a single `contents` turn — intent is stateless per message, history adds noise to classification.

### 5. Silence the noisy demo logs

`create-demo-agent-service.ts:145,153` log `[demo] LLM config: ...` and `[demo] replyStrategy configured: ...` on every request. These appear in the smoke output and pollute production logs. Gate them behind `process.env.DEBUG_LLM === 'true'` (default off).

## What does NOT change

- **The system prompt text** (`system-prompt.ts`) — it's already strong and contains the educational content. Touched in item #3 (sistema-guía), not here.
- **The 7 tool declarations** (`llm-tools.ts`) — function calling shape is unchanged.
- **The regex `IntentParser` fallback** — still the safety net when the LLM errors/times out.
- **The `LLMProvider` port** (`{generateWithTools, generateText}`) — signature unchanged; only the implementation internals evolve.
- **The `AgentChatResponse` shape** — frontend stays compatible.
- **`MODEL_FALLBACKS = []`** — intentionally empty. 3.6 is verified working; a fallback list would re-introduce the "wrong model" risk. On 3.6 failure, fall back to the **template** reply (existing path), not to another model.

## Architecture

```
routes/agent.ts  ─POST /agent/chat──►  AgentChatService.handleMessage
                                            │
                                            ├─ parser.parse(msg)  ──► LlmIntentParser
                                            │                           └─► GeminiProvider.generateWithTools
                                            │                                  · model from DEFAULT_LLM_MODEL / LLM_MODEL
                                            │                                  · generationConfig {temp, topP, maxTokens:2048}
                                            │                                  · AbortController 15s
                                            │                                  · skips `thought:true` parts
                                            │
                                            └─ replyStrategy.buildReply(scenario, ctx) ──► GeminiProvider.generateText
                                                                                          · multi-turn contents (history)
                                                                                          · generationConfig + timeout
                                                                                          · skips thoughts
                                            │
                                            └─ on any LLM error/timeout → templateReply (existing safety net)

app.ts /health ──► uses SAME model source (no more hardcoded URL)
```

Boundaries:
- **`GeminiProvider`** owns: HTTP, model name (received), generationConfig, timeout, thoughts-skipping, retry. Pure adapter.
- **`LlmIntentParser` / `LlmReplyStrategy`** own: which method to call, how to assemble `contents`/`tools`/`systemInstruction`. Domain-facing.
- **`factory.ts`** owns: the default model constant, wiring.
- **`app.ts /health`** consumes the constant; does not duplicate it.

## Testing

All tests use mocked `fetch` or injected fake providers — no network.

1. **`gemini-provider.test.ts`** (extend):
   - Response leading with a `{thought: true, text: "internal reasoning..."}` part then the real `{text: "answer"}` → returns `"answer"`, not the thought. *(new — guards the 3.6 thinking quirk)*
   - `functionCall` present after a thoughts part → still routed correctly.
   - `fetch` aborts after `GEMINI_TIMEOUT_MS` → returns `err` with a timeout-typed DomainError.
   - Request body includes `generationConfig: {maxOutputTokens: 2048, temperature: 0.7, ...}`. *(assertion, not just absence)*

2. **`factory.test.ts`** (update):
   - `createLlmProvider` with no `LLM_MODEL` → provider constructed with `gemini-3.6-flash`.
   - `LLM_MODEL='custom-x'` → provider constructed with `custom-x`.
   - Test fixtures stop using real model strings; use `'test-model'`.

3. **`app.test.ts` / `/health`** (extend):
   - `/health` builds the probe URL from the same source as the chat — when `LLM_MODEL` is set, the health probe hits that model. (Mock `fetch`; assert the URL contains the configured model, not a hardcoded one.)

4. **`llm-reply-strategy.test.ts`** (extend):
   - `generateText` is called with multi-turn `contents` (array of `{role, parts}` turns), not a single inlined-text turn.
   - Final user turn still carries the scenario framing text.

5. **No new network tests.** A live smoke against the real API (item #10 of the build queue) covers end-to-end; unit tests stay hermetic.

## Error handling

- **Timeout** → `err(timeoutDomainError)` → caller falls back to template reply. Judge sees a (templated) answer, never a hang.
- **404 / model not found** → existing non-retryable path returns `err` with the body snippet; same template fallback. This is the safety if a future `LLM_MODEL` typo points at a non-existent model.
- **Empty/truncated reply** (`finishReason: MAX_TOKENS` with empty text) → treat as empty string; template fallback kicks in (existing behavior). The `maxOutputTokens: 2048` sizing makes this vanishingly rare.
- **Thoughts leak** → prevented by the parser change; verified by the new regression test.
